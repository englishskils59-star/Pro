## جاهزية ML محليًا
يوجد 2,603 override، لكن أعمدته لا تتضمن مراجعًا بشريًا أو وقت اعتماد أو إصدار تعريفات أو نص الملاحظة نفسه. يمكن ربطه بالزيارة لأغراض التطبيق، لكن لا يكفي وحده لإثبات مجموعة تقييم مستقلة موثقة. لم نستخدم نتائج البرنامج كـGround Truth، ولم ندرّب أو نفعّل نموذجًا أو نعلن Accuracy.
أضيف classification_corrections.py منفصلًا: record_correction يستلزم record_id والنص الأصلي والحالة المعتمدة وapproved_by وsource وdefinitions_version، ويسجل UTC وإصدارًا append-only؛ approved_labels يقرأ آخر اعتماد مع إبقاء التاريخ. لا تنشأ أي SQLite إلا باستدعاء حفظ صريح إلى مسار مستقل يختاره المشغل، ولا تُستورد overrides التاريخية آليًا.
evaluation_groups يجمع النصوص المتطابقة وشبه المتطابقة كمكونات مترابطة لمنع توزيعها بين التدريب والاختبار. قبل تجربة TF-IDF char n-grams مع Logistic Regression محليًا يجب جمع عينة بشرية موثقة وتمثيل الفئات وفصل العملاء والزمن ومجموعات التشابه. إن تعارضت قيود الفصل تُخفض البيانات أو يُبلغ تعذر التقييم، ولا تُسرب السجلات. عندها فقط تقارن Rules Only وML Only وHybrid بمقاييس per-class ومعدل الامتناع وتغطية القرار على نفس الاختبار، مع حفظ إصدار المرشح وعدم تبديل المحرك تلقائيًا.
لا خدمات خارجية أو نقل بيانات خارج الجهاز أو تدريب على توقعات المحرك.

## قيود وأسئلة تعريف تجاري
المعالجة الحالية حتمية وقاعدية ومحافظة، وليست فهمًا لغويًا عامًا. حدود النفي وروابط الجمل وقائمة الجهات ليست شاملة لكل العامية أو كل الموردين؛ الغموض قد ينتج Unclassified. اختلاف النتيجة ليس تحسن دقة مثبتًا.
1. في ملاحظة تجمع رفضًا واهتمامًا أو تعاملًا سابقًا ونية رجوع، هل تعتمدون آخر تصريح واضح زمنيًا أم إبقاء مراجعة بشرية؟ الوضع الحالي يمتنع عن الحسم ولا يخترع أولوية جديدة.
2. هل الوعد بطلب/اتفاق مستقبلي دون اهتمام صريح يُعد Potential Customer وفق تعريفكم؟ حاليًا لا يُعتبر تعاملًا مكتملًا ولا يفرض حالة جديدة.
لم تنفذ واجهة مراجعة جديدة. المقترح عند طلبها لاحقًا: جدول مستقل يعرض معرف الزيارة والنص وقرار القواعد وسبب التعارض والقرار البشري مع هوية المراجع والتاريخ والإصدار، واعتماد صريح فقط دون إعادة تدريب تلقائي. يحتاج اعتمادًا منفصلًا قبل التنفيذ.
